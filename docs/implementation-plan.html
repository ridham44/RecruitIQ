Rules that keep today's features working

Every phase below follows these rules. If a change can't meet one of them, redesign the change.

  1. Migrations only add things. Add new tables, add new columns that are nullable or have a default, and append new enum values. Never rename or drop a column during this plan. Existing rows must stay valid without a backfill. When a backfill is needed, it goes in the same migration as plain SQL.
  2. New behavior is off by default. Each new automatic behavior sits behind a per-job setting or an env flag. Its default reproduces what the app does today, e.g. Job.autoAdvanceOnMatch = false and interviewFlow = SLOT.
  3. Keep the old paths. Slot booking, manual Shortlist/Reject, the "Run screening" button, candidate self-registration and the existing /company/* and /candidate/* routes all stay. New flows run alongside them.
  4. The COMPANY role still means "owner of a recruitment company". The existing Company table is the Recruitment Company. It gets extended, not renamed, so every current companyId reference keeps working.
  5. Empty settings leave AI prompts unchanged. When a recruiter hasn't filled in the new interview or evaluation instructions, the question-planning and report prompts must be byte-for-byte what they are today.
  6. Enum values get their own migration. Postgres can't use an ALTER TYPE … ADD VALUE value in the same transaction that adds it. Put enum additions in their own migration, applied before any code that writes the new value.
  7. Comment old code out instead of deleting it (team convention). Every edited file keeps the replaced lines as comments.
  8. Responsive from the start. Every new page (admin, recruiters, clients, careers portal, OTP, HR portal) is built mobile-first with Tailwind and checked at 320, 375, 768, 1024 and 1440px, as CLAUDE.md requires.

PHASE 1

Platform Admin & onboarding by admin only

§1, §1.1, §15risk lowsize M

A Platform Admin creates and manages Recruitment Companies. When the flag is turned off, companies can no longer register themselves.

Database (additive)

// new enum — separate migration
enum CompanyStatus { ACTIVE  SUSPENDED }

model Company {
  // …existing fields unchanged…
  status      CompanyStatus @default(ACTIVE)
  slug        String?       @unique   // careers portal URL, used in P4
  createdByAdminId String?
}

Existing companies become ACTIVE automatically. Role.ADMIN already exists.

Backend

  • scripts/create-admin.mjs: creates the first ADMIN user from env or CLI arguments. There's no public admin signup.
  • New module src/server/modules/admin/, mounted at /api/v1/admin with authenticate, authorize(ROLES.ADMIN):
    • GET /companies (search, status filter, job/candidate counts)
    • POST /companies: creates the Company + owner User (role COMPANY) in one transaction and emails the owner a set-password link
    • PATCH /companies/:id edit · PATCH /companies/:id/status
    • GET /users · PATCH /users/:id/status (activate/deactivate any user)
  • Set-password flow: a PasswordToken table (userId, tokenHash, purpose, expiresAt, usedAt) plus POST /auth/set-password. It's reused for recruiter and HR invites later.
  • login in auth.service.js rejects COMPANY users whose company is SUSPENDED. The authenticate middleware checks the same thing, so existing tokens stop working after a suspension.
  • POST /auth/register/company returns 403 SELF_REGISTER_DISABLED when ALLOW_COMPANY_SELF_REGISTER=false. The route stays in the code.

Frontend

  • New /admin layout, protected by role ADMIN: companies (table on desktop, cards on mobile), companies/new, companies/:id, users.
  • New /auth/set-password?token=… page.
  • RegisterPage.jsx: hide the "Company" tab when the flag is off (expose it via GET /api/v1/config/public). The candidate tab doesn't change.
  • Login redirect: ADMIN → /admin/companies.

Keeps working because

  • No existing table changes shape. Companies registered earlier log in as before.
  • Self-registration stays on until you change the env flag, so turn it off only after an admin exists.

Done when

  • The admin creates a company, the owner sets a password, logs in and sees the normal company dashboard.
  • A suspended company's owner can't log in, and an already-issued token gets 403.
  • With the flag off, the company tab is hidden and the API returns 403.
PHASE 2

Recruiters & permissions

§2, §3, §15risk highsize L

A recruitment company has many users. The owner adds recruiters, sets their permissions and assigns them to clients and jobs. Recruiters work only inside what they're given.

Why this is the riskiest phase

Ownership checks look up prisma.company.findUnique({ where: { userId } }) in about 34 places across 9 service files (jobs, applications, screening, scheduling, interviews, interviewConfig, resumes, companies). All of them need to go through one helper. Do this refactor as a separate first PR with no behavior change, run the smoke test, and only then add recruiters.

Database (additive + backfill)

enum MemberRole { OWNER  RECRUITER }

model CompanyMember {
  id          String     @id @default(cuid())
  companyId   String
  userId      String     @unique      // a user belongs to one recruitment company
  role        MemberRole @default(RECRUITER)
  permissions String[]   @default([])  // see list below; OWNER implicitly has all
  isActive    Boolean    @default(true)
  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt
  company Company @relation(fields: [companyId], references: [id], onDelete: Cascade)
  user    User    @relation(fields: [userId], references: [id], onDelete: Cascade)
  jobAssignments    JobRecruiter[]
  clientAssignments ClientRecruiter[]   // added in P3
  @@index([companyId])
}

model JobRecruiter {           // §3 "Associate Recruiter with Jobs"
  jobId    String
  memberId String
  @@id([jobId, memberId])
}

-- backfill in the same migration: every existing company owner becomes an OWNER member
INSERT INTO "CompanyMember"(id, "companyId", "userId", role, "isActive", "createdAt", "updatedAt")
SELECT gen_random_uuid()::text, c.id, c."userId", 'OWNER', true, now(), now() FROM companies c;

Company.userId stays as the owner's user ID. New users get Role.RECRUITER, which already exists in the enum.

Step A: refactor with no behavior change

  • New src/server/modules/companies/companyContext.js: getCompanyContext(userId) → { companyId, memberId, role, permissions, isOwner }. It looks up CompanyMember first and falls back to Company.userId.
  • Rewrite getCompanyIdForUser and getOwnedJob in jobs.service.js to use it. Then replace each inline company: { userId } check in the other services with getOwnedJob or the context helper.
  • Add ROLES.RECRUITER next to ROLES.COMPANY in every authorize(ROLES.COMPANY) call (jobs, applications, screening, scheduling, interviews routes).
  • Run the smoke test. It must pass unchanged.

Step B: recruiter features

  • Permission keys: MANAGE_RECRUITERS, MANAGE_CLIENTS, MANAGE_JOBS, REVIEW_CANDIDATES, CONFIGURE_INTERVIEWS, SUBMIT_CANDIDATES. Kept in src/shared/constants/permissions.js.
  • Middleware requirePermission(key) uses the context. OWNER always passes.
  • Scope: a RECRUITER sees only jobs they're assigned to (via JobRecruiter) or created themselves, plus jobs under clients they're assigned to (P3). The OWNER sees everything. Enforce it inside getOwnedJob and listCompanyJobs.
  • Endpoints /api/v1/recruiters: list, invite (creates User + Member + set-password email), edit, PATCH /:id/status, PUT /:id/permissions, PUT /:id/jobs.
  • Deactivating a recruiter sets both member.isActive and user.isActive to false. Their jobs stay and the owner can reassign them.

Frontend

  • /company/recruiters: list (cards on mobile), invite modal, permission checkboxes, job assignment multi-select, activate/deactivate toggle.
  • RECRUITER users use the same /company/* layout. Hide nav items and buttons they don't have permission for, using a usePermissions() hook fed by /auth/me (which now returns membership).
  • Job detail: an "Assigned recruiters" field.

Keeps working because

  • Every current company user gets an OWNER member in the backfill, so all ownership checks give the same result.
  • The helper falls back to Company.userId, so an owner the backfill somehow missed still gets in.
  • The refactor ships and is tested alone before any new permission logic exists.

Done when

  • The smoke test passes after step A with no code changes to it.
  • A recruiter assigned to job X can review X's applicants and gets 403 on job Y.
  • A deactivated recruiter can't log in.
PHASE 3

Client companies, departments, HR & job linkage

§4, §4.1, §4.2, §5risk mediumsize M

Recruitment companies manage their clients, each client's departments and each department's HR / hiring people. Every new job can be linked to a client, department and HR person.

Database (additive)

model ClientCompany {
  id            String   @id @default(cuid())
  companyId     String                      // owning recruitment company
  name          String
  description   String?
  website       String?
  industry      String?
  contactName   String?
  contactEmail  String?
  contactPhone  String?
  address       String?
  isActive      Boolean  @default(true)
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  recruiters    ClientRecruiter[]
  jobs          Job[]

}

model Department {
  id              String @id @default(cuid())
  clientCompanyId String
  name            String                    // IT, Finance, Sales…
  isActive        Boolean @default(true)
  hiringPersons   HiringPerson[]
  jobs            Job[]
  @@unique([clientCompanyId, name])
}

model HiringPerson {
  id           String  @id @default(cuid())
  departmentId String
  fullName     String
  email        String
  phone        String?
  designation  String?
  userId       String? @unique              // filled in P8 when invited to the portal
  isActive     Boolean @default(true)
  jobs         Job[]
  @@index([departmentId])
}

model ClientRecruiter { clientCompanyId String  memberId String  @@id([clientCompanyId, memberId]) }

model Job {
  // …existing…
  clientCompanyId String?
  departmentId    String?
  hiringPersonId  String?
}

All three job links are nullable. Existing jobs keep working with no client attached.

Backend

  • New module src/server/modules/clients/: CRUD for /clients, /clients/:id/departments, /departments/:id/hiring-persons, plus PUT /clients/:id/recruiters. All gated by MANAGE_CLIENTS and scoped to ctx.companyId.
  • Use soft deactivation (isActive=false), not hard delete, so old jobs and submissions keep their links.
  • createJob/updateJob check that the chain belongs together: the HR person belongs to the department, the department to the client, and the client to ctx.companyId. Otherwise return 400 INVALID_CLIENT_CHAIN.
  • Add clientCompanyId, departmentId and hiringPersonId to createJobSchema/updateJobSchema as optional fields.

Job = title + description (§5)

  • Make the structured job fields optional in the form and the schema (they already have DB defaults). Show a short job form with title, description, client → department → HR and recruiters, plus an "Advanced" section that holds the current fields.
  • Leave the screening prompt as it is. It already works from the description, and when structured fields are empty it uses only the description.
  • Check that deterministic.util.js handles an empty requiredSkills (the skill-overlap score should be neutral, not 0).

Frontend

  • /company/clients list → /company/clients/:id with tabs for Info, Departments (each opens to show its HR people) and Recruiters.
  • Job new/edit: three dropdowns that depend on each other (client → department → HR). Show client and department on job cards and the job list.
  • Filter jobs and the dashboard by client.

Keeps working because

  • Jobs without a client behave exactly as today. Nothing downstream requires the new fields until P7, and P7 falls back gracefully.
  • The advanced job fields stay available. Only "required" is relaxed.

Done when

  • You can create Client → IT dept → HR person, create a job linked to them, and see it on the job page.
  • A job created with only title + description can be screened and interviewed.
PHASE 4

Candidate portal, OTP, auto matching & best-job match

§6, §7, §8risk mediumsize L

A candidate uploads a CV with or without choosing a job, confirms their phone with an OTP, and is matched automatically. When the score passes the job's threshold, they move straight to the interview stage.

Database (additive)

enum ApplicationSource { DIRECT  GUEST  AUTO_MATCH }

model PhoneOtp {
  id         String    @id @default(cuid())
  phone      String                   // E.164
  codeHash   String
  purpose    String    @default("APPLY")
  attempts   Int       @default(0)
  expiresAt  DateTime
  verifiedAt DateTime?
  createdAt  DateTime  @default(now())
  @@index([phone, createdAt])
}

model CvSubmission {                 // §6 Option B — CV without a job
  id           String   @id @default(cuid())
  companyId    String                // which recruitment company's portal
  candidateId  String
  resumeId     String
  status       String   @default("PENDING")   // PENDING | MATCHED | NO_MATCH | FAILED
  matchResults Json?                 // top-N job scores
  applicationId String?  @unique     // the Application created for the best job
  createdAt    DateTime @default(now())
}

model Candidate   { phoneVerifiedAt DateTime? }
model User        { passwordSet Boolean @default(true) }   // guest users get false
model Application { source ApplicationSource @default(DIRECT) }
model Job         { autoAdvanceOnMatch Boolean @default(false) }  // §8 threshold → interview

SMS & OTP

  • New src/server/modules/notifications/sms/ using the same driver pattern as email: console.driver.js (dev, prints the code) and twilio.driver.js (reuses the Twilio credentials from phone-agent). The driver is picked by SMS_DRIVER.
  • POST /public/otp/send {phone}: 6-digit code, 5-minute expiry, stored as a bcrypt hash. Rate limits: at most 3 per phone per 15 minutes and 10 per IP per hour.
  • POST /public/otp/verify {phone, code}: at most 5 attempts. Returns an otpToken (JWT, 15 minutes, holds the phone number) that the apply call requires.

Guest apply (§6A)

  • POST /public/cv/parse (multipart): stores the file and runs the existing resume-analyzer. Returns the name, email and phone it found so the form can prefill them. Returns an upload ID.
  • POST /public/applications {uploadId, jobId?, fullName, email, phone, otpToken}:
    1. checks that the phone in otpToken matches the phone submitted
    2. finds the Candidate by email, or creates User (random password, passwordSet=false) + Candidate
    3. creates the Resume from the upload, then either an Application (source=GUEST) or a CvSubmission
    4. emails "Set a password to track your application" (reuses PasswordToken from P1)
  • If the email already belongs to an account with a password, still accept the application and tell the candidate to log in to track it.

Auto screening on apply (§8)

  • After applyToJob (the existing logged-in flow) and guest apply, call screenApplication. It's currently internal in screening.service.js, so export a screenApplicationById wrapper that doesn't take a userId.
  • On Vercel, run it inside the request with a timeout guard and return the application with status: SCREENING. The client polls GET /public/applications/:id/status until the result is ready.
  • New logic in screenApplication, only when job.autoAdvanceOnMatch is on: score ≥ minAcceptableScore → SHORTLISTED + create the interview invite (P5). Below it → REJECTED + the existing rejection email.
  • When the flag is off, behavior is exactly today's: the application stays SCREENING and the recruiter decides.

Best-job match (§6B)

  • New src/server/modules/screening/bestMatch.service.js:
    1. load that company's OPEN jobs
    2. pre-rank them for free with deterministic.util.js skill overlap plus a title/keyword match on the description
    3. run the AI screening on the top 3–5 only, to keep costs down
    4. take the highest score; if it's ≥ that job's threshold, create an Application (source=AUTO_MATCH) and continue as in 6A
    5. otherwise set NO_MATCH and send a "we'll keep your CV" email
  • Store every job's score in matchResults so recruiters can see why.
  • New screen /company/cv-pool: CvSubmissions and their scores. Recruiters can manually apply a CV to any job.

Frontend

  • A public careers portal at /careers/:companySlug (list + search) → /careers/:companySlug/jobs/:id → apply wizard. Also /careers/:companySlug/submit-cv for applying without a job.
  • Wizard steps: Upload CV → Confirm details (prefilled) → Verify phone (6 digit boxes, resend timer, inputmode="numeric", autocomplete="one-time-code") → Matching… (polling) → result screen (rejected, or interview link from P5).
  • Single column and touch-friendly on phones. The file drop area also works as a plain file input on mobile.
  • Keep the existing /candidate/jobs apply flow for logged-in candidates. It also gets auto-screening, and OTP when phoneVerifiedAt is empty.

Keeps working because

  • The public routes are new (/api/v1/public/*, /careers/*) and are also behind FEATURE_GUEST_APPLY.
  • autoAdvanceOnMatch defaults to false, so existing jobs screen and decide exactly as today. The "Run screening" button and bulk Shortlist/Reject still work, and re-running screening is safe.
  • Guest users are ordinary Candidate users, so the candidate dashboard, application detail and interview room work for them once they set a password.

Done when

  • A guest applies with OTP, gets screened automatically and sees the result within about 30 seconds.
  • A CV without a job gets placed on the best-matching job, or marked NO_MATCH.
  • A job with auto-advance off behaves exactly as before, and the smoke test passes.
PHASE 5

Instant interview link (attend now or later)

§9risk mediumsize M

When a candidate passes the match, they see a secure interview link right away. They can start now, or send the link to themselves by email or SMS and use the same link later. No slot booking is needed.

Database (additive)

enum InterviewFlow { SLOT  INSTANT }

model Job       { interviewFlow InterviewFlow @default(SLOT)
                  inviteValidDays Int @default(7) }

model Interview {
  slotId          String?          // was required → now optional (relaxing NOT NULL is safe)
  accessTokenHash String?  @unique
  inviteExpiresAt DateTime?
  inviteSentAt    DateTime?
}

enum EmailType { … INTERVIEW_INVITE }        // own migration

Backend

  • createInstantInterview(applicationId) in scheduling.service.js: creates an Interview with no slot, mode=ONLINE, a random 32-byte token (only its SHA-256 hash is stored) and inviteExpiresAt. It sets application.status = INTERVIEW_SCHEDULED and returns the link /interview/<token>.
  • It's called from P4 auto-advance when job.interviewFlow = INSTANT, and from a new recruiter button "Send instant interview link" on shortlisted applicants.
  • POST /public/interviews/:token/session: checks the hash, the expiry and that status isn't COMPLETED. Returns a candidate JWT scoped to that interview (role: CANDIDATE, interviewId, 3 hours).
  • Update the authenticate middleware to accept scoped tokens. interviews.controller checks that req.user.interviewId (if present) matches :interviewId. The existing start/answer/events/end endpoints and LiveKit token handling are reused unchanged.
  • POST /public/interviews/:token/send {channel: "email"|"sms", to?}: defaults to the candidate's own email or verified phone. Limited to 3 sends per interview per hour. Logged in EmailLog (or an SmsLog).
  • The same link keeps working until the interview is COMPLETED or expires. If the connection drops, the candidate can rejoin the IN_PROGRESS interview.

Null-slot audit (important)

Anything that reads interview.slot.* has to handle a missing slot:

  • scheduling.service.js: cancel/reschedule, and the listing sort by slot.startTime. Instant interviews sort by createdAt.
  • interviewEngine.service.js: any "too early / too late to start" window check is skipped for INSTANT and uses inviteExpiresAt instead.
  • email.service.js: the confirmation template prints the slot time. Use a separate invite template.
  • Phone worker: /worker/phone-interviews/due filters on mode=PHONE, so INSTANT (ONLINE) interviews never reach it. Confirm this.
  • UI: JobInterviewsPage.jsx, InterviewDetailPage.jsx and ApplicationDetailPage.jsx show "On-demand" when there's no slot.

Search for slot. and slotId across src/ and phone-agent/ before merging.

Frontend

  • Result screen after matching: Start interview now (primary) · Send me the link (email / SMS tabs) · the link itself as copyable text.
  • New public route /interview/:token: pre-check page (camera and mic test, instructions) → mounts the existing InterviewRoomPage with the scoped token. It doesn't need the /candidate layout or a login.
  • Job settings: an "Interview flow: Slot booking / Instant link" toggle.

Keeps working because

  • interviewFlow defaults to SLOT, so every current job keeps slot booking. Existing interviews all have a slot, so the null-safe code behaves the same for them.
  • The interview engine, LiveKit, monitoring events and report generation aren't touched. Only how the candidate gets in is new.
  • Phone interviews stay slot-based.

Done when

  • A candidate passes the match, clicks Start now and finishes the interview. The report is generated as today.
  • Choosing "later" sends the link by email and SMS, and opening it the next day works. A completed or expired link shows a clear message.
  • Slot-booking jobs (online and phone) still work end to end.
PHASE 6

Recruiter interview & evaluation instructions

§10, §11risk lowsize S

Recruiters write free-text guidance on what to ask and how to score. The AI uses it together with the job description and the CV.

Database (additive)

model AiInterviewConfig {
  // …existing (aiName, questionCount, customQuestions…)…

  evaluationInstructions String?   // scoring criteria/weights — max 2000 chars

Backend

  • Add the fields to upsertInterviewConfigSchema as optional, trimmed, with a length limit.
  • interviewConfig.service.js getEffectiveConfig: default the new fields to null / [].
  • interviewEngine.service.js, question planning: only when present, add a "Recruiter guidance" section to the prompt. Put it inside delimiters and label it as guidance on topics, not as commands that can override the rules.
  • Report generation: only when present, add "Recruiter evaluation criteria" and ask for a criteriaAssessment array (criterion, met / partly / not met, evidence). Store it inside the existing InterviewReport.questionAnalysis JSON or in a new nullable criteriaAssessment Json?.
  • Phone agent: return the same fields from /worker/context so phone interviews follow the instructions too.
  • Keep the existing fairness rule: remove any demographic words from the guidance before it reaches the prompt (same rule as screening).

Frontend

  • In the existing interview config panel (job interviews page), add two textareas with character counters and example placeholders:
    • "Check hands-on experience with Kubernetes; ask about a production incident they handled."
    • "System design counts double; communication must be at least 6/10."
  • InterviewDetailPage.jsx: a "Recruiter criteria" card showing met / partly / not met for each criterion.

Keeps working because

  • When both fields are empty, the prompts are identical to today. Add a unit test that compares the built prompt string with and without the fields.
  • Custom questions and question limits are untouched.

Done when

  • With instructions set, the interview visibly covers the requested topics, and the report lists the criteria.
  • With them empty, the prompt snapshot test passes.
PHASE 7

Final score, final threshold & submission to client

§11, §12, §13risk mediumsize M

Combine the CV match and the interview into one final score, compare it with the job's final threshold, and send qualified candidates to the right Client → Department → HR person.

Database (additive)

// own migration — append only
enum ApplicationStatus { … QUALIFIED  NOT_QUALIFIED  SUBMITTED_TO_CLIENT }
enum EmailType         { … CLIENT_SUBMISSION }

model Job {
  finalThreshold       Float?               // null = feature off for this job
  cvWeight             Float   @default(0.3)
  interviewWeight      Float   @default(0.7)
  autoSubmitToClient   Boolean @default(false)
}

Backend

  • New src/server/modules/submissions/finalScore.service.js: computeFinalScore(application) = cv × cvWeight + interview × interviewWeight, with the weights normalized to add up to 1. Called from interviewEngine.service.js right after the report is saved as COMPLETED (around line 567).
  • Only when job.finalThreshold is set: ≥ threshold → QUALIFIED, below → NOT_QUALIFIED. When it's null, the status stays INTERVIEW_COMPLETED as today.
  • POST /submissions {applicationId, hiringPersonId?} (SUBMIT_CANDIDATES permission): defaults to the job's HR person. It builds the snapshot: candidate name, email and phone; CV file reference; job title and ID; CV–job score, matched/missing skills and reasoning; interview overall/technical/communication scores, strengths, areas for improvement and criteria assessment; final score; plus a question-by-question summary. Then sets SUBMITTED_TO_CLIENT and sends the HR person an email with a secure link (the portal from P8, or a signed read-only link before P8 ships).
  • When autoSubmitToClient is on and the result is QUALIFIED, the same service submits automatically.
  • The snapshot freezes the data, so later re-screening or report regeneration doesn't change what the client received.

Keeps working because
